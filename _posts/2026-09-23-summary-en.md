WordPress is a widely used open-source Content Management System \(CMS\) built with PHP, known for its extensibility through plugins and themes but also a frequent target for security research due to its massive install base.

## [vLLM v0.30.0 introduces persistent GPU weight-cache for faster restarts and new model support.](https://github.com/vllm-project/vllm/releases/tag/v0.30.0) ⭐️ 7.0/10

vLLM v0.30.0 was released, introducing a persistent per-GPU weight-cache daemon that allows engines to restart by mapping weights via CUDA IPC instead of reloading from disk, significantly speeding up engine recovery. The release also adds support for several new models like DeepSeek-V4.1-Flash and includes numerous performance optimizations for models such as Qwen3.8-Flash-Next and Kimi K3. This release is significant because the persistent weight-cache feature drastically reduces downtime during engine restarts, which is critical for maintaining high availability in production LLM serving environments. The addition of new model support and deep performance optimizations keeps vLLM at the forefront of high-throughput, low-latency inference, directly benefiting developers and companies deploying large language models at scale. The Fast Start feature uses a daemon per GPU to hold post-quantized, tensor-parallel-sharded weights in GPU memory and is activated with the \`--load-format ipc\_cache\` flag. For DeepSeek-V4.1-Flash, the entire KV cache is stored in MXFP8 format using the FlashMLA V4.1 record, but this specific optimization is currently only available on SM100 \(H200\) GPUs.

github · khluu · Sep 22, 05:20

**Background**: vLLM is a high-throughput and memory-efficient inference and serving engine for large language models \(LLMs\). A key challenge in LLM serving is the time it takes to load model weights from disk into GPU memory when restarting an inference engine, which can cause significant downtime. The new persistent weight-cache daemon addresses this by keeping the weights resident in GPU memory between engine sessions, allowing subsequent engines to map to that memory directly via CUDA Inter-Process Communication \(IPC\).

## [FoxScript: A Rust/WASM Runtime Revives Legacy Visual FoxPro](https://foxscript.org/) ⭐️ 7.0/10

A new runtime called FoxScript has been released, which allows Visual FoxPro 9 code to run on a modern stack. It is built in Rust, compiled to WebAssembly, maintains backward compatibility with 32-bit .fll add-ins, and adds modern features like lambdas, JSON support, and an HTTP server. This matters because it provides a potential lifeline for countless legacy business applications that are too costly or risky to rewrite, allowing them to run on modern 64-bit systems and integrate with web technologies. It demonstrates a novel approach to preserving critical business logic while incrementally modernizing a deprecated technology stack. The project removes the 2 GB table size limit of the original FoxPro and is released under the MIT license. However, it is currently an early-stage project with reports not yet implemented and builds being unsigned, indicating it is not yet production-ready.

hackernews · boredjohnny · Sep 22, 21:00 · [Discussion](https://news.ycombinator.com/item?id=49808023)

**Background**: Visual FoxPro \(VFP\) is a data-centric programming language and IDE, part of the xBase family, which Microsoft officially discontinued in 2007. Its runtime is 32-bit only, and many business applications built with it remain in operation due to the high cost of replacement. WebAssembly \(WASM\) is a portable binary instruction format that allows code written in languages like Rust to run efficiently in web browsers and other environments, enabling legacy code reuse.
